# Автотесты «Школы сноуборда»

UI-тесты платформы обучения сноуборду на pytest. Репозиторий отдельный от приложения — код продукта здесь не лежит и не правится.

Что проверяется в первую очередь — **доступ к платному контенту**. Уроки и разборы катания продаются по подписке, и утечка платного мимо пейволла для этого продукта дороже любого дефекта вёрстки.

Набор существует в двух реализациях. Это ветка `playwright`: к набору на Selenium здесь добавлены **те же проверки** регистрации и пейволла, переписанные на **Playwright**, — чтобы сравнить инструменты на одинаковых сценариях, а не на разных. Что из этого вышло — в разделе «Ветка `playwright`» ниже. Законченный набор только на Selenium лежит на [`main`](../../tree/main).

## Что нужно для запуска

- Python 3.12 или новее
- Google Chrome (драйвер Selenium скачивает сам, ставить `chromedriver` не надо)
- Поднятый стенд приложения на `http://127.0.0.1:8000`

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

## Запуск

```bash
pytest                      # все тесты, кроме ratelimit (см. ниже)
pytest -m smoke             # быстрая проверка, что стенд жив
pytest -m paywall           # только доступ к платному
pytest -m signup            # регистрация: форма и валидация полей
pytest -m api               # проверки на уровне HTTP, без браузера
pytest -m ratelimit         # только отдельно — исчерпывает лимит на минуту
pytest --headless           # без окна браузера
pytest --base-url http://127.0.0.1:8000   # другой адрес стенда
pytest --collect-only -q    # что вообще собирается, ничего не запуская
ruff check .    # проверка оформления и импортов
```

## Адрес стенда

Адрес по умолчанию задан в `pytest.ini` строкой `base_url = http://127.0.0.1:8000`. Флаг `--base-url` перекрывает его для одного запуска.

Сам параметр объявляет плагин `pytest-base-url`, а не `conftest.py`, — и своё объявление заводить здесь нельзя. Два объявления одного параметра, и pytest не стартует вовсе: падает на загрузке `conftest.py` с `ValueError: option names {'--base-url'} already added`. Выглядит это как поломка всего репозитория, хотя ни один тест ни при чём.

Плагин, в отличие от прежней самодельной фикстуры, не срезает слеш в конце: `--base-url http://127.0.0.1:8000/` даст в запросах двойной слеш. Адрес пишем без слеша.

## Ветка `playwright`: вторая реализация

Эта ветка существует, чтобы сравнить два инструмента на одном и том же наборе, а не чтобы заменить один другим. На `main` лежит законченный набор на Selenium; здесь часть тестов регистрации переписана на Playwright.

Дополнительно к общей установке нужен браузер — Playwright работает не с системным Chrome, а со своей сборкой Chromium:

```bash
playwright install chromium
```

```bash
pytest tests/test_signup_pw.py            # только тесты на Playwright
pytest tests/test_signup_pw.py --headed   # с окном браузера
```

Перенесены целиком два файла. Регистрация — все шесть тестов из `test_signup.py`: счастливый путь, слабый пароль с тремя наборами, пустая форма, негодный адрес с пятью наборами, регистрация без страны и пароль, похожий на адрес. Пейволл — все три теста из `test_paywall.py`: подписчик видит плеер, аноним и три роли без подписки видят заглушку.

На одинаковых сценариях разница такая. Playwright короче на ожиданиях: вместо `WebDriverWait` с явным условием — `expect(...)`, который сам ждёт до таймаута, поэтому отдельных ожиданий в тестах нет вовсе. Он же сам параметризует набор по браузерам: `test_signup_leads_to_confirm_email[chromium]`, и Firefox с WebKit подключаются флагом `--browser` без правок в коде. Взамен он строже к неоднозначным локаторам — `get_by_label("Пароль")` падает, если на странице есть ещё и кнопка «Показать пароль», — и не умеет проверять «не меньше четырёх», только точное количество.

Подпись «Пароль» в Playwright берётся с `exact=True` — иначе локатор ловит ещё и кнопку-глаз «Показать пароль», появившуюся на форме входа, и падает со strict mode violation: по умолчанию `get_by_label` ищет подстроку без учёта регистра.

Отдельно в `test_paywall_pw.py` перенесён `test_subscriber_gets_player` — ради приёма, которого нет в Selenium-части. Вход под `student` выполняется **один раз за прогон**: сессионная фикстура проходит форму, сохраняет куки через `context.storage_state(path=...)`, а каждый тест стартует в новом контексте с этим состоянием. Изоляция остаётся полной — контекст свежий, — но форму входа тест больше не проходит, и в теле остаётся два действия вместо семи.

Файл состояния кладётся во временную папку pytest (`tmp_path_factory`), а не в репозиторий: внутри рабочий `sessionid`, и кто его получил, тот вошёл под этой ролью. Между прогонами он всё равно протухает, поэтому хранить его незачем.

Сохранять состояние можно только после того, как сервер поставил `sessionid`, — поэтому между нажатием «Войти» и сохранением стоит `expect(page).to_have_url(...)`. Без этого ожидания в файл попадёт пустое состояние, а тесты потом упрутся в пейволл без внятной причины. Маркеры сохраняются — `pytest -m signup` находит обе реализации, поэтому в отчёте они различаются именем файла, а не именем теста: имена функций в двух файлах совпадают намеренно.

Имя теста в отчёте выглядит как `test_signup_leads_to_confirm_email[chromium]`: плагин сам параметризует тесты по браузерам. Firefox и WebKit ставятся тем же `playwright install` и подключаются флагом `--browser`, правок в тестах не требуется.

Своя параметризация с браузерной перемножается: `test_weak_password_is_rejected[chromium-Abc12!]`. Три набора данных на одном браузере дают три теста, на двух — шесть, и всё это без единой правки в коде.

**Локаторы здесь живут в самом тесте, а не в `pages/` — это решение, а не недоделка.** Ради одного-двух тестов страничный объект не окупается, а смысл ветки в том, чтобы сравнить инструменты в равных условиях: сколько строк занимает то же самое без обвязки. Если тестов на Playwright станет заметно больше, договорённость про `pages/` вернётся в силу.

Проверка количества ошибок в Playwright только точная — `to_have_count(5)`, аналога «не меньше пяти» в библиотеке нет. Selenium-версия подтянута к тому же: было `len(alerts) >= 4`, стало `== 5`. Обе реализации проверяют одно и то же, иначе сравнение инструментов теряет смысл. Заодно точная проверка ловит случай, когда форма начнёт дублировать ошибку.

Ошибок именно пять, а не четыре, с 01.10.2026: в форму добавили два обязательных согласия — на обработку персональных данных и о возрасте, — а поле «Пароль (ещё раз)» убрали. Три «Обязательное поле.» плюс два отдельных текста про согласия.

Пустую форму отбивает сервер, а не браузер. `required` у полей есть, но на самой форме стоит `novalidate` — браузерная проверка отключена намеренно, чтобы все ошибки приходили в одном оформлении, через `[role=alert]`. Поэтому отправка доходит до бэкенда и возвращается с пятью ошибками. Если `novalidate` когда-нибудь уберут, `test_empty_signup_form_is_rejected` покраснеет в обеих реализациях: форма просто не отправится. Это будет ожидаемое изменение поведения, а не дефект.

Ошибки формы ищутся так же, как в Selenium-части, — по `[role=alert]`, только средствами Playwright: `page.get_by_role("alert")`. Фильтр `.filter(has_text=...)` нужен потому, что форма показывает несколько ошибок сразу, а Playwright отказывается проверять «какую-то одну из» и требует однозначного локатора.

## Тест лимита запускается отдельно

Регистраций allauth пропускает двадцать в минуту с одного адреса, дальше отвечает `429`. Тест `test_too_many_signups_are_throttled` этот лимит намеренно исчерпывает — и следующие пятьдесят секунд любой тест регистрации получает `429` не по вине продукта.

Поэтому он вынесен под свой маркер и **исключён из обычного прогона**: в `pytest.ini` стоит `-m "not ratelimit"`. Команда `pytest -m ratelimit` этот фильтр перекрывает и запускает только его.

Восстановить состояние после такого теста нельзя — минуту всё равно ждать. Изоляция здесь единственный работающий приём.

**Запускать его не сразу после полного прогона, а выждав минуту.** Обычный прогон отправляет около тринадцати регистраций за пятнадцать секунд и почти выбирает лимит. Запущенный следом тест получает `429` со второй-третьей попытки — зелёный, но проверивший не работу защиты, а остаток чужого счётчика.

Чтобы такой прогон не выдавал себя за настоящий, тест первым делом убеждается, что стартовое состояние чистое: `codes[0] != 429`. Красный с текстом «лимит был исчерпан до начала теста» — это не дефект продукта, а сообщение, что проверку запустили не в тех условиях.

## Лимит неудачных входов

Неудачных попыток входа allauth пропускает пять за пять минут — и по адресу, и по учётным данным (`login_failed: 5/5m/ip,5/5m/key`). Негативный тест входа тратит две попытки за прогон: два прогона подряд проходят, третий за те же пять минут упрётся в лимит.

Изолировать этот тест, как тест лимита регистраций, нельзя: неудачный вход — это и есть его предмет, отдельного маркера тут не хватит. Поэтому тест сам распознаёт ситуацию и говорит о ней прямо, вместо того чтобы падать с невнятным «форма ответила не то»:

```python
assert "Слишком много" not in shown, "лимит неудачных входов исчерпан, проверка не показательна"
```

Увидели это сообщение — подождите пять минут, дефекта здесь нет.

## Лимит на письма с кодом

Подтверждение почты идёт шестизначным кодом из письма, и письмо нельзя отправлять чаще **раза в десять секунд на адрес**. Это задевает единственный тест — `test_unconfirmed_email_cannot_log_in`: он регистрируется и сразу пробует войти, а вход с неподтверждённой почтой заставляет сайт переслать код. Без паузы форма отвечает «Слишком много неудачных попыток входа» — хотя пароль верный и попытка первая. Поэтому в тесте стоит `time.sleep(11)` с объяснением: это единственное место, где пауза оправдана, и почему — сказано ниже, в договорённостях.

Сверх частоты у приложения есть свои потолки: **пять кодов в час и десять в сутки на адрес**. Поэтому тест регистрируется каждый раз на новый адрес `autotest-*` — с постоянным аккаунтом набор упёрся бы в потолок после пятого прогона за час, а суточный держал бы до утра.

## Когда тест падает

Фикстура `driver` снимает экран браузера в момент падения и складывает картинку в `screenshots/<имя теста>.png`. Путь печатается в выводе pytest, в разделе «Captured stdout teardown». Папка в git не попадает — это результат прогона, а не исходник.

Снимок делается и когда падает подготовка теста, а не сама проверка: например, если не сработал вход. Это тот случай, где скриншот полезнее всего — по тексту ошибки видно только, что фикстура не доехала, а на картинке видно, что именно показал браузер.

## Перечисление пользователей закрыто в трёх точках

Если форма отвечает по-разному на существующий и несуществующий адрес, список клиентов сервиса собирается перебором — без всякого взлома. Дверей, где это возможно, ровно три, и незакрытая обесценивает остальные:

| Где | Тест |
|---|---|
| Регистрация | `test_signup_with_existing_email_does_not_reveal_it` |
| Вход | `test_login_with_bad_credentials_is_rejected` — «неверный пароль» и «несуществующий адрес» дают одну ошибку |
| Сброс пароля | `test_password_reset_does_not_reveal_whether_email_exists` |

Это одно требование, проверенное во всех точках, где оно может сломаться, а не три отдельных теста.

## Роли на стенде

Пароль у всех — `demo12345`.

| Роль | Вход | Что должна видеть |
|---|---|---|
| Ученик с подпиской | `student@demo.kz` | урок открыт, на странице плеер |
| Тренер | `coach@demo.kz` | очередь разборов `/coach/`; уроки — пейволл |
| Админ | `admin@demo.kz` | админка `/admin/`; уроки — пейволл |
| Без подписки | `guest@demo.kz` | пейволл на уроке |
| Аноним | — | каталог открыт; `/reviews/` и `/coach/` — редирект на вход |

Роль сама по себе доступа к платному не даёт — его даёт только подписка. Поэтому тренер и админ упираются в пейволл наравне с гостем, и это не дефект.

Пароли лежат в репозитории открыто только потому, что стенд локальный и данные в нём выдуманные. Для любого настоящего окружения креды берутся из переменных окружения.

## Что нужно от стенда

Стенд поднимается из репозитория приложения:

```bash
docker compose up -d
docker compose exec app uv run python manage.py loaddata demo   # курсы, уроки, тарифы
docker compose exec app uv run python manage.py seed_demo       # демо-аккаунты и подписка
```

Три вещи, без которых тесты упадут не по вине продукта:

**Почта аккаунтов должна быть подтверждена.** У приложения `ACCOUNT_EMAIL_VERIFICATION = "mandatory"`, а `seed_demo` запись о подтверждении не создаёт — вход отбрасывает на `/accounts/confirm-email/`. На свежем стенде это правится вручную через админку или shell.

**Переменные `BUNNY_*` в `.env` приложения не должны быть пустыми.** С пустым `BUNNY_TOKEN_KEY` страница урока отвечает ошибкой сервера: подпись ссылки незаданным ключом — это ошибка конфигурации, а не тихая деградация. Для разработки годятся заглушки.

**Демо-подписка не вечная.** `seed_demo` выдаёт `student@demo.kz` подписку на тридцать дней. Когда срок выходит, `test_subscriber_gets_player` краснеет: подписчик видит пейволл вместо плеера. Выглядит как дефект доступа, хотя продукт отработал правильно — подписки действительно нет. Проверить и обновить:

```bash
docker compose exec app uv run python manage.py shell -c \
  "from django.apps import apps; print([(s.user.email, s.ends_at) for s in apps.get_model('billing','Subscription').objects.all()])"
docker compose exec app uv run python manage.py seed_demo
```

Учти, что у истёкшей подписки поле `status` остаётся `active` — доступ считается по `ends_at`, так что ориентироваться надо на дату, а не на состояние.

**Чистка тестовых данных.** Каждый прогон оставляет на стенде пользователей `autotest-*` — их создают тесты регистрации. Удалять через Django, а не `DELETE` в psql: у пользователя есть связанная запись о подтверждении почты, и ORM удаляет её каскадом сама.

```bash
docker compose exec app uv run python manage.py shell -c \
  "from apps.identity.models import User; print(User.objects.filter(email__startswith='autotest-').delete())"
```

## Если упали сразу все тесты

`ERR_CONNECTION_REFUSED` в браузерных тестах и `ConnectionError` в HTTP-тестах означают, что стенд не отвечает. Продукт тут ни при чём: упало всё разом и одинаково, включая давно стабильные тесты.

Частый случай — контейнер приложения выключился, а база и очередь остались работать. Со стороны выглядит как «всё поднято, а сайт не открывается».

```bash
docker compose ps -a          # какие контейнеры живы; смотреть на состояние app
docker compose logs app --tail 30   # почему выключился
docker compose up -d          # поднять заново
```

Типичная причина в журнале — `OperationalError: failed to resolve host 'db'`: приложение стартовало раньше, чем стала доступна база, и завершилось. Лечится повторным `docker compose up -d`, когда база уже здорова.

## Известное ограничение

С заглушками вместо настоящих ключей Bunny видео в плеере не проигрывается. Поэтому тесты проверяют, что плеер вставлен в страницу и ссылка ведёт на Bunny, но не само воспроизведение. Сценарии «видео реально играет» потребуют стенда с настоящими ключами.

## Договорённости

- Никаких `time.sleep` — только `WebDriverWait` с явным условием. Неявное ожидание держится на нуле: смешивать его с явным нельзя. Единственное исключение — `test_unconfirmed_email_cannot_log_in`, где ждать приходится не отрисовку страницы, а истечение серверного лимита на отправку письма: в браузере в этот момент ждать нечего, и `WebDriverWait` бессилен. Исключение помечено комментарием в коде, иначе следующий человек просто удалит строку.
- Локатор ищет элемент так, как его находит человек (по видимой надписи), а проверка смотрит на результат (адрес, наличие элемента). Один и тот же признак не может быть одновременно способом поиска и предметом проверки.
- Локаторы живут в `pages/`, а не в тестах. Тест говорит `SignupPage(...).open().fill(...).submit()` и не знает, каким селектором ищется поле: вёрстку правят в одном классе, а не в десяти тестах. Проверки при этом остаются в тестах — страница только отдаёт данные (`errors()`), решать, что считать правильным, — не её дело.
- Ожидание смотрит на признак нового состояния, а не на то, что уже истинно. После выхода адрес не меняется (`/courses/` до и после), поэтому ждём появления ссылки «Войти», а не смены адреса. Ожидание условия, верного в момент вызова, не ждёт ничего и оставляет гонку с перезагрузкой страницы.
- Выход двухшаговый: кнопка в шапке открывает диалог «Точно выйти?», разлогинивает кнопка внутри него. Диалог лежит в разметке всегда, поэтому ждать его надо через `element_to_be_clickable`, а не `presence_of_element_located` — иначе проверка вернётся до открытия, и клик упрётся в невидимый элемент.
- Проверка идёт на самом низком уровне, на котором её видно. Права доступа — это код ответа (`200`, `403`, редирект на вход), поэтому они проверяются запросами, а не браузером: те же проверки в Selenium занимали 36 секунд против 0,4. В браузер выносится только то, что без него не проверить, — вёрстка, клики, видимость элементов.
- Классы Tailwind (`text-[15px]`, `font-semibold`) в локаторы не берём — это оформление, оно меняется при любой правке дизайна. Атрибутов `data-testid` в шаблонах приложения пока нет, они запрошены у разработчика.
- Каждый новый тест проверяется на управляемом отказе: сломать то, что он сторожит, и убедиться, что он краснеет. Тест, который ни разу не падал, ничего не доказывает.
